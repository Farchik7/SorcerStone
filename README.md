# Проблеми та аналіз початкового коду 


1. Весь процедурний код виконання програми розміщений в одному монолітному методі `main()`, що повністю порушує принцип єдиної відповідальності (Single Responsibility Principle).
2. Логіка читання файлу, очищення тексту регулярними виразами, підрахунок частоти слів та сортування з виводом не розділена на окремі спеціалізовані методи.
3. У початковій реалізації використовувався баг із методом `distinctString.contains(words[i])`, який перевіряв підрядок, а не окреме слово, через що слова, які є частиною інших (наприклад, "he" всередині "the" або "other"), помилково пропускалися під час пошуку унікальних слів.
4. Накопичення унікальних слів за допомогою конкатенації рядків (`distinctString += words[i] + " "`) створює величезну кількість зайвих об'єктів у незмінній пам'яті `String`, що критично навантажує Garbage Collector.
5. Алгоритм підрахунку частоти слів реалізований через вкладені цикли (O(N^2)), що призводить до катастрофічного падіння продуктивності на великих об'ємах тексту.
6. У сигнатурі методу `main` використовується просте прокидання винятків через `throws IOException` замість їхньої локальної обробки за допомогою блоків `try-catch`.
7. Числові обмеження для виводу результатів (`30` для топ-слів) жорстко зашиті в код у вигляді «магічного числа» замість того, щоб бути винесеними в іменовану константу.


# Оптимізація пам'яті та продуктивності

## 1. Оптимізація споживання пам'яті
* Повністю усунуто накопичення унікальних слів через конкатенацію рядків (`+=`), що виключає створення тисяч проміжних об'єктів у Heap-пам'яті та розвантажує Garbage Collector.
* Застосовано потоковий підхід із використанням `Files.lines()` та `Stream API`, що дозволяє обробляти великий текстовий файл «на льоту» рядок за рядком без збереження зайвих проміжних масивів у пікову пам'ять.
* Завдяки використанню потоків та попередньо скомпільованих патернів регулярних виразів знижено навантаження на оперативну пам'ять під час обробки великих об'ємів даних.
* **Код першої версії рефакторингу виконувавася за 293 мс, а фінальна оптимізована версія зменшила час виконання до 255 мс завдяки поточному зчитуванню файлу та мінімальному піковому споживанню оперативної пам'яті.
